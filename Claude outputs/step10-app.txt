STEP 10: SERVE THE PAGES (strata/app.py + strata/templates/)
FastAPI routes; Jinja2 templates; uvicorn runs it. No JavaScript beyond form submission.
Every GET calls events.replay and renders the State. Every POST appends one event and
redirects back.

================================ THE ROUTES ===================================

  GET  /projects/{id}/review          review.html   the main page
  GET  /projects/{id}/queue           queue.html    expert queue
  GET  /projects/{id}/audit           audit.html    event list + rollback
  GET  /projects/{id}/state?upto=N                  state as of event N (json)

  POST /projects/{id}/versions                      load the next version, run pipeline
  POST /tasks/{id}/approve                          append task_approved
  POST /tasks/{id}/edit                             append task_edited (with signature
                                                    and lineage keys computed here)
  POST /tasks/{id}/escalate                         append task_escalated
  POST /tasks/{id}/create-obligation                append node_created (+ edge_created)
                                                    and resolve the expert task
  POST /projects/{id}/rollback                      append rollback

============================== WHAT make run DOES =============================

  make reset      delete strata.db, ingest v1 v2 v3 and meridian.json
  bootstrap       run_version(v2)  from cache, no key needed
  uvicorn         serve on http://localhost:8000

So the review page is populated on first load with the v1->v2 result.

============================== DESIGN NOTES ===================================

Server-rendered so the whole product stays in one language. Three templates, no
client-side state. The verification badge, the confidence, and the path are on
every item so the decisions that matter are visible in the product and not only
in the code.

Tasks hang off the change, not the claim, because a merged task has no single
owning claim. Claims render above as evidence; tasks render below as work.

The edit form is the R4.4 path: it looks up the change, computes the edit signature
and the lineage key, and writes both into the task_edited payload. Without that the
correction would be recorded but never found again.
